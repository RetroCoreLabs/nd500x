# Symbol Table Corruption Issue and Solution

## Summary

The pcc-nd500 linker has a **symbol table corruption bug** that truncates symbol names and corrupts the string table. This issue cannot be avoided, but we work around it by using the `.map` file for symbol resolution instead of the embedded symbol table.

## The Problem

When linking object files (even a single object file) to create an executable, the pcc-nd500 linker corrupts the symbol table:

**Symptoms:**
- Symbol names truncated to 3-4 characters
- String table contains garbage
- Most symbols show as `(null)` or random fragments

**Example:**
```
Expected:        Got:
_kernel_main  →  ain
_init_kernel  →  ler
_scheduler    →  ler
_proctab      →  roc
```

### Conclusion

**The pcc-nd500 linker has a fundamental bug in its symbol table / string table handling.**

This corruption happens:
1. ✓ With or without `-x` flag (preserve locals)
2. ✓ With single object file
3. ✓ With multiple object files (worse)
4. ✓ Regardless of source file structure

**The bug is in the linker, not our code.**

## The Solution: Use .map Files

Since the linker corrupts embedded symbols, we use **separate symbol map files** instead.

### How It Works

**Step 1: Assembler generates .map file**
```bash
nd500-as -am kernel.s -o kernel.o
# Creates: kernel.map (line number → address mapping)
```

**Step 2: Linker updates .map with final addresses**
```bash
nd500-ld -m -o kernel kernel.o
# Updates: kernel.map with relocated addresses
```

**Step 3: Debugger loads .map separately**
```javascript
// In JavaScript (WASM debugger)
await this.handleMapUpload(new File([mapContent], 'kernel.map'));

// In C (native debugger)
ndlib_map_load("kernel.map");
```

**Step 4: Symbol resolution uses .map**
```c
const char* symbol = ndlib_symbols_lookup_addr(address);
// Returns: "_kernel_main" (from .map, not from symbol table)
```

### Map File Format

**Example kernel.map:**
```
; Source: kernel.s
; Assembly line → Address mapping

0000000A  _kernel_main
00000021  _sys_read
00000036  _sys_exit
00000122  _init_kernel
000001F3  _scheduler
```

**Map file contains:**
- Symbol names (full, not truncated)
- Addresses (relocated by linker)
- Source file line numbers
- Type information

### Advantages

✓ **Full symbol names** - No truncation
✓ **Reliable** - Generated by assembler, not corrupted by linker
✓ **Complete** - Includes all symbols (local + global)
✓ **Source mapping** - Line numbers for source-level debugging

## Implementation in kernel.zip

### Files Included

## Build Process (Current)

### Makefile Steps

```makefile
# Step 1: Preprocess locore.c → locore.s
$(CC) -E -DLOCORE locore.c > locore.s

# Step 2: Compile kernel.c → kernel.s
$(CC) -S kernel.c -o kernel.s

# Step 3: Combine locore.s + kernel.s
cat locore.s kernel.s > kernel_combined.s

# Step 4: Assemble with map generation
$(AS) -am kernel_combined.s -o kernel.o
# Generates: kernel.map (GOOD SYMBOLS!)

# Step 5: Link (corrupts symbols, but updates .map)
$(LD) -i -e start -m -o kernel kernel.o
# Updates: kernel.map with final relocated addresses
# Corrupts: kernel symbol table (BUT WE DON'T USE IT!)

# Step 6: Package everything
zip kernel.zip locore.c locore.s kernel.c kernel.s kernel kernel.map
```

**Key:** We include `kernel.map` in the ZIP, which has GOOD symbols.

## Future Considerations

### If pcc-nd500 Linker is Fixed

If the linker bug is eventually fixed:
1. Embedded symbols would work correctly
2. `.map` files would still be generated (no harm)
3. Debugger would prefer embedded symbols over .map (faster)
4. Fallback to .map if embedded symbols missing

### Alternative: Use nm-style External Symbols

Could generate external symbol file from object files:
```bash
# Extract symbols before linking (while still good)
nd500-dump -s kernel.o > kernel.sym

# Use kernel.sym instead of corrupted embedded table
```

But `.map` files are better because they include source line mappings.

## Conclusion

**Problem:** pcc-nd500 linker corrupts symbol tables

**Impact:** Embedded symbols are unusable for debugging

**Solution:** Use `.map` files generated by assembler/linker
- ✓ Full symbol names
- ✓ Source line mappings
- ✓ Already implemented in WASM and native debuggers
- ✓ Included in kernel.zip

**Status:** ✓ **RESOLVED** (via workaround)

The kernel works correctly, debugging works correctly, symbols resolve correctly - all thanks to the `.map` file, NOT the corrupted symbol table.
